# 知养：Agent 需求规格

状态：与当前 `main` 试用版一致。日期：2026-10-07。

饮食主路径走 `/api/diet`。模型负责看懂，程序负责算数和选题。返回之前再核对一遍。旧的 `POST /api/agent` 仍保留紧急短路和返回检查，不是现在的记录入口。

## 1. 总分工

| 能力 | 模型做什么 | 程序做什么 | 绝不能做什么 |
| --- | --- | --- | --- |
| 识图 | 从照片里给出食物名、分量说法、估计克数 | 校验图片格式，压缩在浏览器完成；克数交给计算 | 模型不输出热量。无密钥时不编造一盘食物 |
| 文字拆分 | 有密钥时把一句话分成食物和克数。一道菜保持整名 | 无密钥时按标点做规则拆分，再精确匹配食物表 | 不把「番茄炒蛋」拆成番茄和鸡蛋，除非用户自己分开写 |
| 查表计算 | 不参与乘法 | 本地 CSV 精确匹配；不可计算的具体菜名再问薄荷；按每 100 克乘克数 | 不给未知食物填默认热量。笼统的「外卖套餐」不去查 |
| 报告文案 | 有密钥时根据已经算好的合计写一两句 | 无密钥时用程序句子。句子里的数字必须在允许列表里 | 不新增合计以外的数字、食物或菜谱。不鼓励极端少吃，不写治疗方案 |
| 食谱库推荐 | 有密钥时只解释已经选中的那一道 | 按缺口、剩余热量和谨慎标记从库里选；换一道时排除已看过的编号 | 不发明库外的菜名、做法或营养数字。没有合适的就说没有 |
| 返回校验 | 不参与放行 | 热量必须能按食物编号和克数重算；推荐编号必须在库里；未通过核对的句子不能返回 | 紧急回复里不能夹食物、食谱或建议 |
| 紧急 / 慢病 / 进食障碍分流 | 不判断是不是急救 | 关键词和已确认标记在调用模型之前或生成句子时生效 | 紧急描述之后不继续给食谱。肾病不按蛋白质缺口推高蛋白菜 |

## 2. 识图

有 `DASHSCOPE_API_KEY` 时，带照片的识别走视觉模型。默认请求是 OpenAI 兼容的 `POST {baseUrl}/chat/completions`，Bearer 密钥。未设置 `DASHSCOPE_BASE_URL` 时，基址是阿里云百炼兼容模式，视觉模型默认 `qwen3-vl-flash`。改成蚂蚁数科大模型平台时，图文都可以设为 `qwen3.8-flash`。

提示词要求只返回 JSON：`items` 里每项是 `name`、`portionLabel`、`grams`。不要热量。照片里分开的食物各自成项。已经是一道菜的，不要再把原料重复列出来。

无密钥且只有照片：直接失败，提示改为打字。`stubImageItems` 里有一份米饭和鸡蛋，当前识别流程没有调用它。

无密钥但有文字：不访问模型，走第 3 节的规则拆分。返回里带 `stub: true`。记录页当前没有单独一句说明这次是规则拆分；面向用户的句子会滤掉「测试替身」等字样。

请求默认 `enable_thinking: false`。超时默认 40 秒。若服务把 `enable_thinking` 当成未知参数并返回 400，会去掉该字段再请求一次。

## 3. 文字拆分

有密钥时用文本模型，默认 `qwen-plus`。蚂蚁数科配置下可以与视觉模型同为 `qwen3.8-flash`。

规则与识图相同：一道菜保留整体名称，例如「番茄炒蛋」「牛肉面」。只有用户明确分开的食材才各自成项。能对上食物表的，用表里的标准名。对不上就保留用户说的短名字。

无密钥时的规则拆分：把「加个」收成一个量词，再按逗号、顿号、「和」「配」等切开；「一个 / 一只 / 一枚」默认 50 克；写了克数就用克数；「小 / 中 / 大」对应分量档。这只为了在没有密钥时把计算走通。

模型返回的名字会去掉括号里的别名，避免把提示词里的别名抄进匹配。

## 4. 查表计算（本地 CSV + 薄荷兜底）

程序步骤：

1. 名字与本地表的名称或别名整段相等才算匹配。不做模糊猜测。
2. 匹配到一条且 `calculable=true`：用该行每 100 克数据乘克数。来源记在结果里。
3. 匹配到多条：状态为待选择，不算热量。
4. 本地没有，或该行不可计算：若允许查询且名字不笼统，调用薄荷。
5. 薄荷请求是 `GET https://api.boohee.com/open-apis/v1/food/search?keyword=食物名`，请求头 `X-Api-Key`。不用文档示例里的 `api.iboohee.com`。
6. 同名优先不带品牌前缀的菜品或食材。热量仍在本机按克数计算。
7. 改已保存的一餐时，若食物编号是薄荷编码，按编码再核对这一条，仍然用本地公式。

本地不可计算、会按名字再问薄荷的：牛肉面、馒头、饺子、小米粥、白粥、面条、挂面、阳春面。

不去查的：外卖套餐、套餐、外卖。

没有 `BOOHEE_API_KEY`、空结果、超时或 HTTP 失败：无法估算，原因分别落到无密钥、未匹配或查询失败。不编数字。

食谱原料必须是可计算的本地食物。茶饮不进这张推荐表。

## 5. 报告文案

程序先按当天各餐重算合计。目标只有在 `confirmed=true` 时才参与对比。

谨慎标记来自两类：用户已确认的勾选，以及记录原文里的关键词（催吐、绝食、暴瘦、只喝茶、不吃饭、孕期、哺乳、未成年、肾病、糖尿病、高血压等）。

有密钥时，把合计、已确认目标和谨慎标记交给文本模型，要求一两句中文，不新增数字、食物或菜谱。程序再用允许的数字列表检查。冲突则整句丢弃，`adviceKept=false` 的句子不会返回给页面。页面改看合计。

无密钥时用程序句子，例如：还没确认目标就说明没有对比；进食相关痛苦时说明不按缺口鼓励少吃；肾病时说明不按蛋白质缺口推荐高蛋白。

全部食物都无法估算时，不给出热量合计。

## 6. 食谱库推荐

程序 `chooseRecipes` 选题，每次取一道：

- 排除配伍检查未通过的菜，以及用户这一轮已经换掉的编号。
- 肾病：去掉 `avoid` 含 `kidney_high_protein` 的菜。
- 进食相关痛苦、孕期、哺乳、未成年、糖尿病、高血压：不按热量缺口加分，改在家常能量附近选。
- 普通人且已确认热量目标：看剩余热量，蛋白质仍少则提高蛋白质更高的菜的排序。肾病不走这条蛋白质加分。

选中之后，有密钥时模型只写理由。理由不能包含其他菜名，数字必须来自合计、目标或这道菜已经算好的营养。否则丢掉，页面仍展示这道菜。

无密钥时理由由程序写，并经过同一套检查。

没有候选时返回说明：食谱库里没有更合适的一道，可以从现有食谱里另选，这里不会新编一道菜。

## 7. 返回校验

`assertDietResult` 在响应离开服务端之前执行：

- 紧急模式的正文必须是固定的 120 提示，且不能带食物项、食谱或建议。
- 已匹配食物的热量、蛋白质、脂肪、碳水必须与按编号和克数重算的结果一致。无法估算的食物不能带营养数字。
- 推荐食谱必须能在库里查到，且没有被配伍规则拦住。
- 未通过核对的建议或理由不能返回。

食物项、目标和请求编号不合法时，接口返回错误，不返回半份结果。

## 8. 紧急、慢病、进食障碍分流

紧急词包括呼吸困难、无法吞咽、胸痛、呕血、昏迷、自伤等。以「什么是」「假如」开头的解释句，以及明确写在过去、当下又没有「现在」的句子，不会被当成这一次急救。这是规则，不是分诊模型。

饮食识别、计算、报告、推荐都会先看文字。命中则只返回急救提示。

非紧急的谨慎分流不阻止记录和合计，只改变建议和选题。详见 [功能需求文档](PRD-功能需求文档.md) 第 3.7 节。

## 9. 密钥与无密钥

| 变量 | 作用 |
| --- | --- |
| `DASHSCOPE_API_KEY` | 有则调用模型。无则文字走规则拆分，纯照片拒绝，报告和理由走程序句子 |
| `DASHSCOPE_BASE_URL` | 兼容接口地址。默认百炼兼容模式 |
| `DASHSCOPE_VISION_MODEL` / `DASHSCOPE_TEXT_MODEL` | 覆盖默认模型名 |
| `BOOHEE_API_KEY` | 只在本地算不了时查询薄荷。可以不填 |
| `INVITE_CODES` / `INVITE_SECRET` | 公网门禁。与模型无关 |

密钥只放在服务端环境变量。浏览器拿不到。不要写入仓库。
