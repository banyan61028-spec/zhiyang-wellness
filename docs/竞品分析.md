# 知养：竞品分析

日期：2026-10-07。作者 linden。

这是桌面研究 / 产品体验对比，不是正式市场调研。没有付费用户访谈，没有问卷样本，没有埋点，也没有评测分数。不写用户规模、留存或付费转化。公开页面上的价格和活动会变，本文不引用。

比较对象只取 [产品方案](10-饮食助手产品方案.md) 第 2 节已经点名的两类：薄荷健康，以及 Keep 这一类把饮食记成热量的产品。用来说明知养把闭环停在哪里。

## 用户做完记录之后，产品停在哪

三类产品都能让人留下「吃了什么」。差别在记录之后的下一步。

薄荷健康在公开使用里，核心是查食物和记饮食。记完，用户看得到热量和营养素。这些数字本身是终点：今天大约多少千卡、蛋白质多少，需要用户自己决定下一顿吃什么。

Keep 一类产品把运动和身体记录放在同一款应用里，饮食或热量记录常常服务于训练和体重目标。记完同样得到一组数字。下一顿的具体菜，仍要用户离开这组数字自己想，或者另找食谱内容。本文没有逐项打开 Keep 的付费饮食功能做核对。

知养的试用版把终点设在下一餐。用户记下这一餐并核对分量之后，「今日」给出合计和一两句话，再从知养自己的食谱库里选一道菜，说明为什么是这道。数字还在，因为没有数字就说不清「缺什么」。数字用来选菜，不是页面的最后一行。

|  | 记下来之后用户先看到什么 | 下一顿从哪来 |
| --- | --- | --- |
| 薄荷健康 | 热量和营养素 | 用户自己决定。知养不把它的食谱库当作自己的推荐来源 |
| Keep 一类 | 热量，以及和运动、体重目标有关的记录 | 用户自己决定。本文不声称已经比对过其全部食谱功能 |
| 知养试用版 | 当天合计，确认过目标才对比，外加一两句话 | 只从知养食谱库选。库里没有合适的就说明没有，不另编一道 |

## 知养因此多出来的要求

既然要说出「缺什么」并给出一道菜，热量就不能由模型随口说。试用版的做法是：

- 对得上本地食物表的，按每 100 克乘克数。
- 对不上、但名字具体的，才按这个名字问薄荷，仍然在本机乘克数。
- 对不上的，界面承认算不出来。
- 推荐菜的编号必须在自己的库里。模型可以写理由，不能新写一道库外的菜。

薄荷在这里是营养查询的兜底，不是知养要做成的产品形态。拍照识别走单独配置的视觉模型，不调用薄荷的图片识别。

## 现在不能声称的优势

桌面对比只能说明闭环不同，不能说明知养已经更好用。下面这些限制都在当前仓库里：

- 食谱是 20 道家常草稿，数据仍标为待审阅。库小的时候，下一餐会经常说没有更合适的。
- 可计算的原料来自美国农业部公开数据并做了四舍五入，不是《中国食物成分表》。牛肉面、馒头、饺子、稀粥、普通面条不能用另一行原料顶上。
- 没有账号。记录留在各自的浏览器里，换设备就没有了。
- 没有运动记录，也不跟训练计划绑在一起。
- 不是医疗器械，不提供诊断或治疗膳食。紧急情况只提示联系当地急救。

若以后要做正式市场判断，需要单独设计访谈或试用记录。在那之前，对外只说：知养试的是「记录之后给下一餐」，样本还是身边少数人的公网试用。
