# 知养：产品设计方案 v0.1

状态：产品草案，MVP 范围待用户确认。本文不代表已经同意所有功能或开始开发。

编写日期：2026-09-12。依据：现有 Demo、此前确认的产品方向和用户提供的竞品报告。

对应范围：[MVP 范围确认单](02-MVP范围确认单.md)。当前实现：[项目说明](../README.md)。

## 1. 这次要做成什么

知养是一款以中式食养、日常茶饮和三餐起居为特色的 AI 健康养生助手。用户可以从自己的目标或身体感受开始交流，也可以先浏览食养内容，再让助手帮助选择、替换和安排。

首版希望让用户完成一件具体的事：把“我想调一调自己的生活”变成一份看得懂、能按现实条件修改、下次还能接着用的饮食或起居安排。

保留现有“首页、食养、调养、我的”四个页面。首页继续突出 AI 咨询，同时保留三餐起居、茶饮、调养专题和文章。用户不必先完成体质测评或填完一大套档案才能开始使用。

产品提供日常生活与食养参考。疾病诊断、治疗性膳食、药物处方和个性化中药组方不属于本轮范围。页面提示只是表达边界的一部分，实际回复与推荐内容也必须遵守同一边界。

## 3. 首批用户与主要问题

首批用户建议选择：对中式食养或养生感兴趣，希望调整饮食、体重或作息，能够自行选择日常食物的成年人。先以本人使用为主。具体年龄分布、职业和性别尚无访谈依据，不在本轮编造人群画像。

| 用户的原话或近似表达 | 实际需要完成的事情 | 当前常见困难：待访谈验证 |
| --- | --- | --- |
| “最近胖了，三餐应该怎么吃？” | 获得符合外食或做饭条件的饮食搭配，能替换不喜欢的食物 | 知道原则，但不清楚怎样放进每天的三餐 |
| “我比较瘦，想把饭吃好一点。” | 查看完整三餐与可选加餐，结合食欲、习惯和时间调整 | 容易把增重理解为只加一种食物，难以形成日常安排 |
| “想喝点养生茶，应该怎么选？” | 看懂原料、准备方式、适用说明，再选择一个明确的饮品 | 内容分散，风味、传统说法和功效容易混在一起 |
| “总觉得湿气重／嗓子不舒服／排便不顺。” | 说清具体感受，了解日常照护参考和何时需要专业帮助 | 不知道从哪类内容查起，也可能把养生内容当治疗 |
| “这顿我做不了，换一个。” | 保留自己的目标和已有安排，只调整做不到的部分 | 每次需要重新交代情况、重新整理回答 |

需要治疗、特殊膳食或药物指导的用户，可以获得明确的使用边界与专业求助提示，不进入本轮个性化食养安排流程。不能因为用户提到“想减重”就直接认定其需要减重。

知养希望验证的差异是：用户的目标、偏好、食养内容和已保存方案可以在一次次咨询之间衔接。通用大模型也能回答养生问题，甚至生成计划；“接入模型”“使用专业提示词”本身不能证明差异化成立。

| 希望形成的体验价值 | MVP 必须出现的可观察行为 |
| --- | --- |
| 少重复交代生活条件 | 用户保存的偏好能在后续咨询中被正确使用，并可修改 |
| 建议与具体内容接得上 | 推荐卡片能打开对应食谱或茶饮详情，来源与说明不互相矛盾 |
| 方案能继续使用 | 从已保存方案进入调整，助手知道原方案；替换一餐时保留其余部分 |
| 更容易选择合适内容 | 遇到不满足条件的内容不强行推荐；没有合适条目时说明原因并给出可行下一步 |

这些是待验证的产品价值，不是现阶段已经建立的竞争壁垒。

## 6. 页面设计与职责

| 页面 | 首要作用 | 首版展示内容及规则 |
| --- | --- | --- |
| 首页 | 让用户开始咨询，或迅速找到今天可用的内容 | AI 主入口；三餐体重、茶饮、作息快捷提问；档案摘要；三餐／起居切换；精选食养；调养专题；短文章 |
| 食养 | 查找和了解具体内容 | 餐食、茶饮、起居、文章分类；详情、收藏、问 AI；首版采用少量人工整理内容 |
| 调养 | 从自己的感受找到生活参考 | 保留 6 个专题：湿气重的感受、嗓子不舒服、排便不顺、作息乱、体重增加、紧绷感；展示生活参考和适用边界 |
| 我的 | 管理自己的选择和后续使用 | 目标与生活偏好、收藏、已保存方案、九种体质科普；可修改、移除与清除本地记录 |

首页默认内容是精选的一般参考。只有确实使用了用户信息时，才标注“结合你的偏好”；时间、日期和时令信息不能继续使用 Demo 的固定日期伪装为实时推荐。

内容详情统一包含：名称、内容类别、原料或准备条件、具体做法／安排、可替换项、适用说明、参考来源及审核状态。餐食和茶饮不使用同一套含糊的功效标签。

## 7. 核心使用流程

### A. 从问题到一份三餐安排

1. 用户在首页选择减重、增重或三餐搭配，也可以自己输入。
2. 助手了解目标和缺失的关键条件，例如做饭／外食、能投入的时间、饮食偏好与相关限制。已经知道的信息不重复问；普通生活偏好允许跳过。
3. 如果涉及是否适合调整体重等关键情况尚不明确，先提供一般搭配参考，不直接设置个人热量或体重目标。
4. 展示早餐、午餐、晚餐；有需要时另列加餐。说明所采用的条件，并提供具体食养内容入口。
5. 用户说“午餐换一个”“不要鱼”“买不到这个”，只替换相关部分，同时说明换了什么。
6. 用户主动保存后，“我的方案”出现对应安排。普通聊天回答不会自动变成已保存方案。

### B. 从茶饮内容到适合自己的选择

1. 用户进入茶饮详情，或向助手提出饮品需求。
2. 结合用户偏好和相关限制，从本轮已经审核的固定饮品条目中选择。
3. 展示原料、准备方式、引用依据与适用说明。AI 可以解释已有内容，不自由增加药材、用量或治疗功效。
4. 没有合适条目或缺少必要条件时，明确说明，允许改看一般饮食、起居内容或寻求专业建议。
5. 收藏饮品，或把符合条件的饮品作为饮食安排的可选补充；饮品不是每份方案的强制组成。

### C. 从身体感受到日常参考

1. 用户选择专题，或描述自己的感受。
2. 助手澄清用户具体指什么，避免把“湿气重”直接转换为某种体质或病因。
3. 在支持范围内给出生活、饮食或休息参考，并连接到审核过的相关条目。
4. 对需要专业处理或明显超出支持范围的情况，给出清楚的下一步；不继续输出看似完整的治疗方案。

### D. 下次继续使用

1. 用户回到“我的”，选择已经保存的方案。
2. 选择“继续调整”，补充“没时间做”“不喜欢”“做不到”等反馈。
3. 助手知道用户选中的是哪份方案、原来如何安排，并提出改动。
4. 用户确认保存更新后替换该方案；只聊天或取消操作不覆盖原方案。

第一版通过用户主动返回和调整来验证重复使用，不加入自动督促、连续打卡或主动消息推送。

## 8. AI 回复的产品要求

每次回复按需要包含：对目标的理解、必要追问、具体建议、推荐内容、适用说明和下一步操作。不强制把每条回答都变成一张方案卡。

三餐／起居方案至少说清：服务的目标、已经采用的生活条件、分项安排、哪些部分可替换，以及哪些信息仍然未知。不能将“未计算热量”的一般搭配包装为精确减重或增重处方。

助手能使用用户当前对话、主动保存的生活偏好和用户选中的旧方案。进入文章或内容详情后的咨询，应知道对应内容是什么。尚未掌握的信息不得编造，否定表达如“没有过敏”不能仅因出现关键词就被当成相反事实。

输入超出支持范围、服务暂时不可用、内容没有候选或保存失败时，要提供清楚的状态和可执行的下一步。失败的回复不能显示为已经生成或保存成功。

## 9. 体质、档案与内容的首版做法

### 体质

九种基本类型为：平和质、气虚质、阳虚质、阴虚质、痰湿质、湿热质、血瘀质、气郁质、特禀质。市场监管总局的发布说明确认了这九种名称，并说明正式辨识涉及体感问题与等级计分方法。[官方发布说明](https://www.samr.gov.cn/xw/sj/art/2026/art_bbc0d96fbbb741a2a66d2f4f7a44fd82.html)

建议内测首版先提供九种体质科普；五题固定结果保留在现有 Demo 供设计参考，退出真实咨询的普通入口，也不送入 Agent 当作个人事实。若用户确认首版必须包含正式测评，再增加正式量表、评分规则、使用条件、来源与结果解释的确认工作。正式测评不能用五题演示直接改名替代。

### 生活档案

建议首版保存：称呼、关注目标、用餐习惯、饮食偏好和准备时间。避免食材及其他相关限制按具体咨询补问，未确认的信息不默认填“没有”。涉及健康状况的内容不默认作为长期档案保存。

建议轻量内测先在当前浏览器保存生活档案、收藏和方案，不做产品账号与跨设备同步；清除浏览器数据可能丢失本地记录，需要提前说明。当前托管站点的访问权限与未来产品账号是两件事。

接真实 Agent 后，完成回答所需的输入会发送给服务端／模型服务。届时必须更新当前“未上传服务器”的说明，明确发送哪些信息，并仅发送完成本次咨询必要的内容。不能把本地保存描述成整条咨询链路完全不联网。

### 内容

建议先准备一个小种子集：8 个餐食搭配（早、午、晚各 2 个，另含 2 个加餐）、2 个茶饮、2 个起居参考、6 个调养专题、3 篇短文章和九种体质介绍。数量是用于覆盖主要流程与替换选择的工作建议，不是行业标准；可以先选素材，再逐条完成审核。

每条用于真实推荐的内容，需要明确出处、具体支持的表述、原料与准备方式、适用条件、审核人和审核日期。传统食养观点与现代营养依据分别标注。不能仅附上一条综合指南链接，就认为某款茶的配方与功效已经被验证。

用户可发挥药学背景参与资料筛选和内容初稿；对于超出自身专业范围的内容，再安排相应专业审核。初期只开放完成审核的条目，无需先建成庞大的知识库或内容管理后台。

## 10. 建议的功能范围

这里的“首版”指下一轮可接真实 Agent 的轻量内测 MVP，尚需范围确认。现有 Demo 不因本文件写入而自动发生变化。

| 编号 | 首版建议必须完成 | 有意控制的规模 |
| --- | --- | --- |
| F01 | 四页导航与首页 AI 主入口 | 沿用当前页面结构，不增加商城或社区 |
| F02 | 真实 AI 咨询、必要追问、内容关联与失败处理 | 重点支持三餐体重和茶饮，兼顾一般作息；症状咨询限已支持专题与使用边界 |
| F03 | 完整三餐／可选加餐、起居安排、单项替换 | 不做精确营养计量或自动一周全量计划 |
| F04 | 食养、茶饮、起居详情与分类 | 先用小种子集，推荐只关联审核过的具体条目 |
| F05 | 六个调养专题与文章 | 固定分类、少量内容，不建设全面症状百科 |
| F06 | 生活档案、收藏、方案保存／移除 | 推荐先保存于当前设备，账号与同步待确认 |
| F07 | 从旧方案继续调整、保存更新 | 带入原方案与反馈；不做打卡、积分、自动推送 |
| F08 | 九种体质科普及清楚的测评状态 | 正式测评是否进首版，待确认；模拟结果不用于真实推荐 |
| F09 | 使用边界、内容来源、数据说明与基本状态反馈 | 核查实际输出行为；不以一条免责声明代替产品约束 |

后续候选：正式体质测评、账号与云端同步、阶段性回顾、更多内容、内容维护界面、知识检索与外部工具接入。是否建设某种知识库或 MCP，由确认范围后的技术方案决定，不先作为功能数量指标。

本轮不做：商城交易、医生问诊、多成员家庭档案、舌诊／面诊、自动中药处方、慢病治疗方案、可穿戴设备接入、复杂任务编排。

## 11. MVP 如何验收

下列是未来实施后的验收要求，不是本轮已通过的测试结果。

| 编号 | 验收场景 | 通过条件 |
| --- | --- | --- |

| A02 | 用户提出三餐、减重或增重目标 | 不先替用户认定医学状态；三餐完整、加餐独立列出，并说明适用条件；对应 F02、F03 |
| A03 | 用户说明不吃鱼或无法做饭 | 建议符合已知限制；替换指定一餐时保留其他安排；对应 F02、F03、F06 |
| A04 | 进入茶饮详情继续咨询 | 助手能引用选中条目；不会擅自加药材、改用量或添加没有依据的功效；对应 F02、F04、F09 |
| A05 | 描述湿气重或专题内的不适 | 不直接判体质、病因；在支持范围内给生活参考，超范围时有适当下一步；对应 F02、F05、F09 |
| A06 | 保存、刷新、继续调整旧方案 | 方案存在；进入时带入原内容；只有保存更新后才改变原方案；对应 F06、F07 |
| A07 | 查看体质页 | 类型和来源可查；没有把演示结果当成用户的真实体质；对应 F08、F09 |
| A08 | 模型失败、无合适内容、保存失败或重复提交 | 有明确状态，不假装成功，不重复生成已保存条目；对应 F02、F06、F09 |
| A09 | 手机与电脑操作 | 主要入口、长回复、详情、表单和方案可读可操作；对应 F01、F04、F06 |
| A10 | 数据使用和删除 | 发送给 Agent 的信息与告知一致；当前设备保存范围可理解，清除功能有效；对应 F06、F09 |
| A11 | 查看文章、收藏和返回详情 | 内容可打开、来源可查、收藏可取消，咨询能带入相关内容；对应 F04、F05、F06 |

功能逻辑变化补充有意义的自动化测试；页面显示用真实浏览器检查。验证集还需包括否定表达、未知限制、缺少候选和越界请求，具体实现写进后续技术方案。

## 12. 小范围体验要验证什么

建议邀请 5–8 位符合首批人群条件的成年人，先观察一次完整使用，再在约一周内了解是否主动回来。这是探索性安排，不代表统计上已验证市场。邀请他人前，需要另行配置合适的访问权限；当前站点仍是仅拥有者可访问。

每人至少尝试：提一个自己的生活目标、修改一次建议、保存一份方案、下次找到并继续调整。记录完成情况、需要帮助的步骤，以及用户觉得省事或不可信的具体原因。

| 验证问题 | 简单记录口径 |
| --- | --- |
| 能不能独立走通 | 完成“提问—修改—保存”的人数／尝试人数，并记录卡住的步骤 |
| 建议是否符合现实 | 用户能否指出一项自己愿意执行的具体安排及其理由 |
| 是否值得再次打开 | 一周内主动返回并查看或调整方案的人数／参与人数；访问不等于健康改善 |
| 相比现有习惯是否省事 | 让用户用自己常用的方法处理同类问题，对比重复输入、整理和修改的困难 |

不预先编造留存或付费目标。首轮先建立基线；如果大多数人需要指导，先修流程；如果能用但没有再次使用的理由，先调整内容与持续使用价值。复盘只记录必要的任务结果和去标识反馈，不默认留存完整健康对话。
