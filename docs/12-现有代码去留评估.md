# 知养：现有代码去留评估

日期：2026-10-03。对照新的饮食助手方向，说明仓库里已有模块是保留复用、冻结，还是要新做。

本次只评估，不改业务代码。结论依据当前 `main` 上的源码。PR #1、PR #3 尚未合并，它们的改动不在这份评估的代码里。

新方向见 [产品方案](10-饮食助手产品方案.md)。

## 总的判断

能留下来接着用的，是本机保存、咨询接口的校验外壳，以及紧急情况分流。食谱数据能当种子，但现在的写法支撑不了「按缺口选下一餐」。

要新做的是食物成分表、热量计算、饮食记录、拍照和文字的结构化结果、当天报告、下一餐选择。这些在仓库里还没有。

体质、茶饮、专题、文章、起居和配伍禁忌先冻结。代码留着，不接到新的主路径上。

## 食谱库具体差在哪

现在的 `recipes` 能展示名称、做法和一句说明，也能被咨询接口引用。它还不能回答「这道菜大约多少热量、蛋白质高不高」。

下一餐推荐需要每道菜至少有：稳定编号、适合哪一餐、食材名称、可食部克数、对应的成分表编号、由计算器得出的热量和三大营养素、不适合哪些情况（例如肾病不作为高蛋白推荐）。

茶饮「陈皮红枣温饮」留在冻结内容里，不参与按营养缺口推荐。

## 本机记录具体差在哪

IndexedDB 库名是 `zhiyang-local-v2`，里面是档案、收藏、方案、测评和草稿。刷新后还在，清除时会一起清掉，这和「先不要账号」是对齐的。

饮食记录不是方案。一道已保存的「家常三餐搭配示例」不能代替「今天中午吃了一碗牛肉面」。新记录至少要能按日期加总。聊天记录现在刷新就没了，饮食记录不能跟着聊天一起丢。

若以后做云同步，这是另一项决定，不在这次评估里先改存储。

## `/api/agent`、风险分流和返回检查

这条链路值得留下的是顺序，不是预设台词：

1. 浏览器里先认出明确的紧急说法，立刻给出 120 求助，不等模型。
2. 服务端限制请求大小、来源和频率，不把健康正文打进日志。
3. 返回结构不合法就拒绝。紧急回复里不能夹食谱。
4. 特殊人群和个人治疗要求走保守回复。

要补上的是饮食这条线自己的检查：

- 热量和三大营养素只接受计算器的结果。
- 推荐菜的编号必须在食谱库里。
- 报告正文如果写出和合计不一致的数字，整句去掉。
- 模型提出修改档案时先问用户，不同意不写。
- 进食障碍、孕期、肾病等场景下，不输出缺口型的「再少吃一点」或高蛋白推荐。

现有的敏感词规则把孕妇、老人、高血压等全部挡在个人建议之外。实现新报告时要改这道闸门，否则普通的「我有高血压，帮我看看今天吃了什么」会看不到记录合计。改的时候保留紧急分流，不要为了能出报告把求助也放开。

## 测评、方案修订和旧咨询

测评流程保持冻结。不要把试测结果放进每天的目标或下一餐。

方案修订号、防止旧页面覆盖新记录，这些机制是好的，可以借给以后「用户确认后才更新某一餐」。旧的「生成三餐示例」「鱼换豆腐」不继续加功能。

## 实现时顺手避开的已知问题

这些问题来自 PR #1 的走查和 PR #3 对代码的核对，不是本次要修的缺陷：

- 从减重话术进入后，保存的方案目标可能是「均衡饮食」。
- 鱼换成豆腐时，午餐和晚餐可能变成同一道菜。
- 首页主按钮的文案不会作为用户消息发送。

新首页如果不再走这套预设咨询，问题会自然离开主路径。在旧页面还留着的时候，不要把这些演示说成已经按用户当餐做了个性化计算。
