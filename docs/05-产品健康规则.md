## 1. 回答原则

开放承接健康问题，以中药养生和食养知识为特色，根据问题、个人情况、具体内容和证据选择回答方式。知识介绍、日常食养安排、需要进一步澄清、专业求助均是正常结果。用户提到头痛、基础病或特殊人群，不会仅因标签被拒答；也不保证每次都产出茶饮或三餐方案。

风险控制优先于建议完整性、个性化和对话转化。服务限于健康养生科普及适用的日常生活参考，不提供针对个人的疾病诊断、治疗决策、用药增减、治疗性剂量或中药处方。“不提供医学建议”不能被解释为对明确紧急情况不给求助提示；及时转向专业服务是本产品的必要边界。

区分三个层次：资料介绍某原料的传统用途；资料支持某类人群的一般原则；资料和用户条件支持本次具体安排。前一层不能自动推出后一层。说明“仅供养生参考”不能使缺乏依据的剂量、配方或疾病判断变得可接受。

产品目标是尽量降低风险，不承诺“零风险”或“规避一切责任”。例如《民法典》第五百零六条规定，合同中有关造成对方人身损害的免责条款无效；不能据此假设一段免责声明足以解决实际责任。本文仅用于界定产品设计，不是对本产品具体法律责任的结论。[S19 法律原文](https://www.court.gov.cn/zixun/xiangqing/233181.html)

本文中的优先级、追问数量及拒绝自动推荐的条件是本项目的设计约束，不冒充国家标准或临床分诊规则。临床示例的依据另列，不宣称已覆盖所有紧急情况、药材和人群。

## 2. 一次对话的决策顺序

1. 读取本次信息并区分本人／他人、现在／过去、肯定／否定、确定／未知，以及用户直接陈述／转述。明确紧急情况立即进入专业求助回复，本轮不继续执行推荐流程。
2. 判断用户是在问知识、描述感受，还是要求安排或修改方案。只问会影响本次回答的必要问题。
3. 非紧急情形查找可引用资料和可推荐内容，核对适用条件、原料、十八反、十九畏、在用药及其他限制；特殊人群和情况采用更保守的放行条件。
4. 给出有依据的解释或草稿；条件不足时继续澄清或限制具体建议，仍可提供适当的一般知识。
5. 核对文字、卡片、来源和规则是否一致，通过后展示。未经核对的回复不得先以逐字输出方式显示给用户。

常规追问初稿建议每轮 1–3 个重点问题，避免一次要求完整病史。这个数量是交互建议；已经知道的信息不重复问，紧急情况下不以问完问题为前提。

### 2.1 明确紧急情况的回复

回复只包含简短关切、当前需要及时专业帮助的说明，以及相应求助途径。可能危及生命或需要立即处理的表现，应明确“立即联系当地急救服务或就近急诊”，不能弱化为一般预约咨询。不诊断病名，不提供居家处理步骤、用药、食谱、茶饮、起居或所谓“等待就医期间的调理方案”。

回复模板草稿：“你描述的情况可能需要紧急医疗评估，请立即联系当地急救服务或就近急诊，由专业医护人员处理。”依据本次明确的信息选取适当求助级别；不以模板声称已经确诊，也不显示未核实的电话或机构。

本轮禁止方案卡、食谱／茶饮卡、继续测评或引导生成方案的按钮，不将紧急回复保存为调养方案。紧急求助提示不能夹在长篇科普、推荐或免责声明末尾。此要求也适用于正在修改旧方案时出现的紧急信息。

对同一问题的紧急信息尚未明确得到处理时，用户说“先配茶”“我承担风险”不能恢复推荐。用户补充已就诊等信息后，可讨论不涉及治疗决策的一般养生知识，不能据其一句“没事了”就宣称风险已经排除。

### 2.2 特殊人群与特殊情况

下表是本产品的保守输出策略，不表示这些人群一律不能咨询，也不宣称已建立完整临床分诊。必要信息或对应资料不足时，不给个性化茶方、药材搭配或疾病相关餐单；直接解释缺口并建议医生、药师或相应专业人员核对，避免连续多轮追问后仍勉强出方案。

| 情形 | 可继续回答 | 具体推荐的限制 |
| --- | --- | --- |
| 孕期、备孕、哺乳期 | 有对应依据的健康科普、一般生活原则 | 结合阶段及具体原料核对；未明确支持或存在限制时不推荐个性化食药物质，不用成人经验推断 |
| 婴幼儿、儿童青少年 | 面向照护者、符合年龄阶段的知识 | 必要时问月龄／年龄；不缩小成人茶方或餐单，资料不足转向专业指导 |
| 高龄、衰弱或多重用药 | 一般食养知识及现有医嘱的生活化理解 | 核对实际用药及相关吞咽、饮食限制；不自动附加“补益”药材 |
| 基础病、肝肾功能问题、复杂合并情况 | 相应指南支持的一般知识 | 不制定治疗性营养方案，不改变现有医嘱；相关限制未知则不生成个人方案 |
| 术前术后、正在接受治疗、疑似不良反应或症状明显变化 | 解释需要专业核对的原因，提供适当求助方向 | 不以茶饮或“排毒、消肿、调经”等方案替代评估；明确紧急时走 2.1 |
| 相关健康信息未知、矛盾或不愿提供 | 不依赖缺失信息的一般科普 | 不默认健康、无过敏、未用药或非孕期；无法判断具体适用性时不放行 |

中药的“慎用”在本产品自动推荐中不能简单转为减量后使用。需要专业判断的特殊用法不由模型自行完成。具体判断仍以原料、人群与问题的可靠资料为依据；保守输出是产品选择，不把全体特殊人群描述为同一种医学风险。

## 3. 信息状态

| 状态 | 例子 | 使用规则 |
| --- | --- | --- |
| 用户明确陈述 | “我在吃某药”“我对花生过敏” | 在本次对话保留原意、对象和时间；具体用药仍需准确名称 |
| 用户明确否定 | “我没有花生过敏” | 只表示用户否认这一项，不能扩大成所有食物均不过敏 |
| 未知／不愿提供 | “药名忘了”“这个不想说” | 不写入“无”；影响具体推荐时解释限制，可继续一般知识 |
| 信息冲突 | 先说不过敏，后说某次出现反应 | 针对冲突澄清；相关原料暂不进入个性化候选 |
| 他人或假设场景 | “如果孕妇想喝呢”“我妈妈有高血压” | 不写成提问者本人的长期档案 |

年龄、孕哺状态、基础病、用药及过敏信息按本次需要收集。不为解释“陈皮是什么”强制填一整套个人资料；也不把用户回答过一个问题视为授权上传全部本机记录。

## 5. 具体推荐的放行条件

明确紧急情况首先终止候选推荐。其他情况下，对每一个候选内容分别记录原料身份、内容审核、十八反／十九畏、相关人群资料、过敏限制、用药相互作用、疾病饮食限制、准备方式与用量资料。各项可为 `supported`、`restricted`、`unknown` 或 `not_relevant`；使用最后一种状态必须说明为何与本次建议无关，不能用于掩盖没查到资料。

只有本次推荐所必需的条件均满足、没有适用的限制、原料和用途均有支持时，才进入具体候选。需要的条件由内容类别和实际问题决定；普通食材的日常搭配不需要虚构一份覆盖世界上所有药物的“全相互作用证明”。

| 检查结果 | 本轮表现 |
| --- | --- |
| 明确紧急情况 | 只作及时专业求助提示，不进入配方、方案或替换候选流程 |
| 有适用限制 | 移除相关候选，简要解释，可继续找符合条件的内容 |
| 必要条件未知 | 追问，或只提供不依赖该条件的一般知识；不填默认“无” |
| 资料不支持具体配方 | 保留概念解释，不输出配方、克数、频率或疗程 |
| 条件满足且内容完成审核 | 可提供该版本的具体内容；模型不能自由增加原料或功效 |

每次决策内部输出：命中规则 ID、缺失信息、允许内容 ID、被限制内容及原因、来源版本、回答模式。只记录必要的技术元数据，不默认持久保存健康正文。

明确的字段检查、版本限制、内容审核状态、原料名单和来源 ID 可以做确定性校验。是否理解了否定、是否存在紧急语义、正文是否暗含治疗承诺，仍需语义判断和人工标注用例；不能声称正则或 JSON 校验就已完整解决。

## 6. 代表性对话行为

以下为产品回复结构示例，不是对真实用户的评估结果，也不是只靠几个固定文本完成开放咨询。

| 用户输入 | 期望的第一步与后续方向 |
| --- | --- |
| “我最近胖了，想吃得清淡一点。” | 先理解目标，再问近期变化和做饭／外食条件；在适用条件足够时给完整三餐，不先指定减重公斤数 |
| “我头痛，能喝什么茶？” | 背景未明时按需澄清；已明确紧急信息时直接及时专业求助，本轮没有茶饮或其他调养方案，不猜测病因 |
| “我有高血压，晚饭怎么安排？” | 不拒答。可解释对应一般食养原则，询问已有饮食要求和相关合并情况，再决定能否给具体搭配 |
| “我正在哺乳，能喝黄芪茶吗？” | 说明该具体食药物质的限制依据；不推荐这个候选，仍可讨论有对应依据的日常饮食问题 |
| “我喝的药名忘了，帮我配养生茶。” | 解释需要核对药名；不猜测相互作用，不自行开方；可继续讨论不依赖该茶方的一般生活安排 |
| “我觉得湿气重，腿肿了。” | 澄清肿胀的发生和变化、伴随不适及已有情况；不把肿胀直接等同湿气，不先开祛湿消肿茶 |

## 8. 版本、审核与接入顺序

先将上述可确定执行的部分变成配置、校验函数和测试替身；这不需要选模型。与模型有关的语义识别和开放对话效果，留到真实服务确定后用同一组用例检查，不能提前记为通过。

来源更新、原料身份变化、审核撤回或新增人群限制都形成版本记录。发现规则冲突时，优先处理当前明确的急迫需求；相关具体推荐暂不放行，同时保留可用的解释和澄清。不要用“一律不答健康问题”掩盖资料不足。
