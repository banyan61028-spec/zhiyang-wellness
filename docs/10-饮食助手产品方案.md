## 1. 一句话

知养：一个懂你吃了什么、会告诉你下一顿怎么吃的饮食助手。

用户记下今天吃的东西之后，知养用大白话说今天吃得怎样、缺什么，并从自己的食谱库里推荐下一餐，说明为什么是这道菜。

这是给普通用户使用的真实产品，不只是课程作业演示。第一版把一件事做完整：记录、看懂今天、决定下一顿。

## 2. 和薄荷健康、Keep 的区别

薄荷健康、Keep 这一类产品，记完往往停在热量和营养素的数字上。用户知道「今天 1800 千卡」，仍要自己判断下一顿吃什么。

知养重在记录之后：

- 用日常说法总结今天吃得怎样，不先堆图表。
- 指出最关键的一个缺口，例如蛋白质偏少、蔬菜偏少，或这一餐明显偏油。
- 从知养自己的食谱库里选出下一餐，并说明理由。理由必须对得上当天的记录，不能另编一道库外的菜。

数字仍然要有，因为没有数字就说不清「缺什么」。差别是数字为下一餐服务，而不是产品的终点。

## 3. 给谁用

第一版面向能自己安排三餐的普通成年人。典型情况是：外食和自己做饭都有，愿意花几十秒记一餐，想知道今天吃得是否大致合理、下一顿怎么补。

下面几类人可以打开产品，但第一版不把他们当成「按个人目标计算热量」的用户，规则见第 6 节：

- 有进食障碍相关表述的人，例如催吐、绝食、只喝茶代替吃饭、要求暴瘦。
- 孕妇、哺乳期妇女，以及未成年人。婴幼儿由监护人描述时同样不适用成人目标。
- 已经在治疗糖尿病、肾病、高血压等慢性病，或正在按医嘱控制饮食的人。

知养提供饮食记录和下一餐参考，不提供疾病诊断、用药建议或治疗性营养处方。

## 4. 第一版只做三件事

### 4.1 轻松记录

两种入口，用户用哪种都行。

**拍照。** 用通用的视觉大模型识别菜品，并估计分量。不自研 YOLO 或其他专用检测模型。识别结果是估算：界面写成「约 X 千卡」，并提供一键修正分量，至少包括小碗、中碗、大碗。用户改完分量后，热量按食物成分表重算，不由模型改数字。

**文字。** 例如「中午一碗牛肉面加个蛋」。模型负责把这句话拆成食物和分量，例如牛肉面一碗、鸡蛋一个。拆完之后的热量同样查表计算。

两种记录都允许用户改食物名称和分量。对不上成分表的食物，标成「这道暂时无法估算」，不填一个看起来合理的热量。

### 4.2 每日分析报告

把当天已经记下的食物加总，对照用户的参考目标，展示：

- 总热量
- 蛋白质、脂肪、碳水化合物

然后用一两句大白话说出最要紧的一点。例如「今天蛋白质偏少，蔬菜还够，下一顿可以补一盘豆腐或鱼」。不放一排图表，不展开维生素和矿物质清单。

没有记录时，说明今天还是空的，不生成一份假报告。目标还没设定时，只给出当天合计，不假装已经和「你的目标」比过。

### 4.3 下一餐推荐

根据当天还缺什么，从知养自己的食谱库里选一道菜，并解释理由。例如「午餐蛋白质偏低，这道菌菇豆腐杂粮饭用豆腐补蛋白质，做法也简单」。

模型可以写这句理由，不能自己发明库里没有的菜名、做法或营养数字。库里没有合适的菜时，直接说没有合适的，并建议用户从现有菜里另选，而不是现编一道。

## 5. 数字和文字各管一段

热量、蛋白质、脂肪、碳水化合物必须来自可靠的食物成分数据。大模型只做四件事：看懂文字、识别图片、写报告里的那一两句话、写推荐理由。

模型不凭空生成数字。服务端拿模型给出的食物名称和分量，去成分表计算；算完再把结果交给模型写人话。返回之后再核对一遍：正文里的数字要和计算结果一致，推荐的菜必须是库里的编号。对不上就丢掉这句，改成只展示算好的结果。

食谱库里的每道菜也按食材克数计算营养，不手写一个「大约 400 千卡」而不注明来源。

参考目标来自公开的人群能量范围，或用户自己确认的数字。它是对照用的参考，不是医生开的处方。数据来源和授权见 [技术路线草案](13-技术路线草案.md)。

## 6. 健康风险边界

旧文档写过「不做个人热量计算」「首版不制定精确热量」。那是上一个产品方向。新方向会估算用户记下的食物，并和一个参考目标对比。本节说明由此多出来的风险，以及第一版怎么处理。

估算做得到的事：按成分表和用户确认的分量，算出「大约吃了多少」，再对照一个标明出处的参考目标。

估算做不到、也不假装做到的事：

- 不把「约 520 千卡」说成精确到个位的测量。分量来自照片或一句口语，误差可能不小。
- 不诊断用户该不该减重、增重，不根据一句「最近胖了」自动设一个很低的目标。
- 不承诺吃完这些就能瘦、能治病。
- 不输出极端低热量、断食、只喝茶代替正餐的计划。

| 情况 | 第一版怎么做 |
| --- | --- |
| 普通成年人，愿意记录 | 可以记、可以出当天报告、可以推荐下一餐 |
| 说出催吐、绝食、只喝茶、暴瘦、极端少吃 | 不给热量缺口方案，不夸奖「吃得很少」，不把目标往下压。提示寻求专业帮助，记录功能可以留下，但报告不再推动继续少吃 |
| 孕妇、哺乳期、未成年人 | 可以帮着把食物记下来。不套用普通成人的减重目标，不按热量缺口推荐「少吃一点」。下一餐只从家常菜里给一般搭配，并写明请咨询医生或营养专业人员 |
| 糖尿病、肾病、高血压等慢病，或正在按医嘱吃饭、吃药 | 可以记录，可以展示一般合计。不把热量缺口当成治疗方案。肾病用户不按「蛋白质不够」去推荐高蛋白菜。明确这不是治疗膳食，具体吃什么以医嘱为准 |
| 呼吸困难、胸痛、呕血、昏迷、自伤等紧急描述 | 沿用现有紧急分流：只提示立即联系当地急救（中国大陆 120），不给食谱、不给报告建议 |

免责声明不能代替上面的限制。旧方案里的紧急分流和「特殊情况不输出个人治疗方案」仍然有效，只是不再用「完全不算热量」来回避正常的饮食记录。

## 7. 第一版范围、明确不做、先冻结

### 要做

- 拍照记录、文字记录、小碗／中碗／大碗这一类分量修正，热量显示为「约」。
- 当天热量和三大营养素合计，对照参考目标，加一两句建议。
- 从自有食谱库选下一餐，并说明理由。
- 食物对不上表时承认估不了。
- 改身高、体重、过敏、疾病等档案前，先让用户确认。
- 紧急情况和第 6 节里的分流。
- 手机和电脑都能完成这三步。

### 明确不做

- 自研 YOLO 或专用菜品检测模型。
- 让模型自由编造菜谱、克数或热量。
- 图表墙、维生素全表、一周自动配餐、打卡积分、消息推送。
- 商城、医生问诊、家庭多成员、舌诊面诊、可穿戴设备、慢病治疗方案。
- 账号和云同步。现有做法是记在当前浏览器里。要不要改，见确认单里待拍板的一项。
- 把产品说成医疗器械或精确的营养治疗。

### 先冻结，不删除

这些功能留在仓库里，首页不再把它们当成主路径。以后若要做「中式食养」特色，再单独决定怎么加回来。

- 体质测评，包括 32 道候选题、计分和九种体质科普
- 茶饮
- 调养专题和养生文章
- 以中药养生、开放健康咨询为主的模拟咨询
- 起居作息示例
- 十八反、十九畏配伍检查。代码和测试保留。第一版食谱用家常食材，不靠这套规则支撑主流程；万一菜谱里出现相关原料，仍然要拦住

冻结不是否定以前的工作，是避免第一版同时做测评、茶饮、咨询和饮食记录。

## 8. 用户怎么用

第一版可以继续用现在的四个页面当外壳，但首页的主任务改成记录。

1. 打开首页，拍照或输入一句话，记下这一餐。
2. 看到识别出的食物、分量和「约 X 千卡」。不对就改分量或改名称，数字跟着重算。
3. 需要时打开当天报告：合计、和目标的差距、一两句话。
4. 看下一餐推荐。点进食谱可以看到食材和做法。不喜欢就换一道库里的菜。
5. 记录留在本机。清除数据前要说明清掉就找不回来。

茶饮、专题、测评仍然可以从原页面到达，但首页不再用「我最近胖了」「推荐一杯养生茶」作为主按钮。那些入口在实现时再收起来，本文件先定方向。

## 9. 验收标准

下面是第一版要达到的行为，不是现在已经做到的事。当前原型还不能拍照识菜，也没有按成分表算热量。

| 编号 | 场景 | 通过条件 |
| --- | --- | --- |
| B01 | 拍一餐 | 返回菜品和估计分量；热量写「约」；改成小碗、中碗或大碗后，数字按成分表变化，不是模型另说一个数 |
| B02 | 输入「中午一碗牛肉面加个蛋」 | 拆成可核对的食物和分量；能对上表的才有热量；对不上的标成无法估算，不补一个假数字 |
| B03 | 看当天报告 | 总热量和三大营养素等于当天记录的合计；有目标时才对比；建议只有一两句，且不引入记录里没有的新数字 |
| B04 | 要下一餐 | 推荐的食谱编号在食谱库中；理由对得上当天缺口；库外菜名不出现 |
| B05 | 没有记录，或目标没设 | 空状态说清楚；不生成假报告，不把默认目标说成已经是用户的个人处方 |
| B06 | 进食障碍相关说法、孕期、慢病 | 按第 6 节分流：不推极端少吃，不把成人减重目标套到孕妇和未成年人，肾病不按蛋白质缺口推高蛋白 |
| B07 | 紧急描述 | 只有急救提示，没有食谱和饮食建议 |
| B08 | 模型要改档案 | 身高、体重、过敏、疾病等写入前有明确确认；用户拒绝则不改 |
| B09 | 保存、刷新、清除 | 记录在本机还在；清除后找不回，并事先说明。若 linden 改选账号同步，本条改成与告知一致的同步和删除 |
| B10 | 手机和电脑 | 拍照或输入、改分量、看报告、打开推荐食谱，两条路径都能完成 |

## 10. 和两份未合并 PR 的关系

### PR #1 诊断报告

[PR #1](https://github.com/banyan61028-spec/zhiyang-wellness/pull/1) 是只读诊断，标题为「诊断：知养原型卡在范围，不在页面」。它的判断是对的：四页、本机档案、32 题试测和带分流的模拟咨询已经能跑，推不动是因为正式体质、专业审核和开放问答绑在同一次验收里。

它建议的下一步是收成「用现有食谱编号安排三餐」。这个切口比旧方案小，但仍然是旧方向：交付物是一份三餐安排，不是「记下吃了什么，再告诉下一顿」。

建议：不要合并。诊断里的三处走查问题记在 [代码去留评估](12-现有代码去留评估.md)，实现新闭环时避开即可，不必为了旧的减重咨询演示单独修。PR 可以在 linden 看过之后关闭。

### PR #3 按旧方向改文档

[PR #3](https://github.com/banyan61028-spec/zhiyang-wellness/pull/3) 做了两件事。一件是把文档改成和代码一致，这些事实是对的，本方案已经吸收：

- 测评是 32 道候选题的试测，不是 5 题并且固定显示平和质。
- 增重示例包含早餐、午餐、晚餐，另有一道加餐。
- 「继续调整」会带上原来的方案编号和修订号，但只能演示有限替换，不是自由改餐。
- 本机保存、一部分规则测试已经在跑。确认单里「代码未改」和技术方案末尾「只写了文档所以没跑测试」是过时的。
- 首页主按钮上的句子点击后不会发出去。
- 把带鱼的一餐换成豆腐时，可能和晚餐变成同一道菜。

另一件是产品决定：下一轮只验收「用现有食谱编号安排早中晚」，其余验收项延后。这仍建立在旧的养生咨询方向上，只是把验收收窄了。新定位换了闭环，这份验收不再使用。

建议：关闭 PR #3，不要合并。事实更正以本文和代码去留评估为准。其中「只验收 N1」的范围不要保留。D1 开放养生咨询、D2 正式体质测评，不再作为当前第一版的决定；D3 本机保存建议先沿用，仍需 linden 确认要不要账号。

## 11. 借鉴了哪份参考实现

参考仓库是 [archie0732/healthy-diet-ai-agent](https://github.com/archie0732/healthy-diet-ai-agent)，许可证 MIT，版权人 archie0732，2026。阅读的是 2026-10-03 的 `main`。值得借鉴的是做法，不是把代码拷进来。不采用它的 Bun、Rust 服务，也不采用 `services/yolo` 里的检测模型。

| 做法 | 出处 | 知养怎么用 |
| --- | --- | --- |
| 工具分开调用：先识别食物，再计算营养 | `knowledge_base/SKILL_INDEX.md` 把 `analyze_food_image` 和 `calculate_nutrition` 分成两步；`agent_skills/vision_model.ts` 只让视觉模型返回识别结果；`agent_skills/calc_tools.ts` 按重量计算 | 采用这个分界。视觉模型和文本模型不输出热量。不采用它那份内置小表：未知食物会落到默认值，这会凭空产生数字 |
| 用配置文件管理提示词和知识来源 | 根目录 `agent_config.json` 指向 `knowledge_base/AGENT.md`、`SKILL_INDEX.md`、`NUTRITION_RULES.md`，并写明启用哪些知识来源 | 提示词、食谱库路径、成分表版本放到配置里，换模型或换数据源时不改业务代码 |
| 营养计算做成工具，而不是写在提示词里 | `agent_skills/calc_tools.ts` 的 `calculate_nutrition`；Rust 侧另有 `services/api/src/utils/calculator.rs` | 只借鉴「计算在模型外面」。Rust 计算器按食物大类估算热量，同样不采用 |
| 改用户档案前先征得同意 | `src/server/profileApproval.ts` 把身高、体重、忌口、疾病等整理成待确认项，约 10 分钟内有效；README 中的 `POST /api/approve` 负责确认。技能索引第 4 节有一句「立刻写入」，以同意流程这份代码为准，不按「立刻写入」做 | 模型只能提出修改。用户点头之后才写入本机档案。含糊说法如「随便」「不知道」不写入 |

不借鉴的部分：YOLO 检测、Bun/Rust 技术栈、知识图谱、卫福部新闻同步、版本感知检索实验、联网搜索后由模型总结健康新闻。那些和第一版的三步闭环无关，也会把范围再次撑大。
