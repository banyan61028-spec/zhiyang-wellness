# 知养：功能需求文档（PRD）

状态：与当前 `main` 试用版一致。日期：2026-10-07。作者 linden。

本文把 [产品方案](10-饮食助手产品方案.md) 和 [范围确认单](11-饮食助手MVP范围确认单.md) 收成面试用的正式 PRD。产品方案写于 2026-10-03，其中「当前原型还不能拍照识菜」是草案当时的句子，不描述现在的试用版。验收做到哪一步，以本文第 6 节为准。

主导航是「记录、今日、食谱、我的」。体质测评和茶饮不是这一版的主路径。

## 1. 背景与目标

知养要做完一件事：用户记下今天吃的东西之后，能看懂今天大约吃了多少，并从自己的食谱库里得到下一餐。

热量、蛋白质、脂肪、碳水来自食物数据，按「每 100 克 × 克数」计算，界面写成「约」。识别食物、估计克数、写一两句建议，交给模型。对不上表的食物标成无法估算。

这一版给身边少数人试用，已经有公网入口。部署和邀请码见 [部署说明](15-公开部署.md)。

## 2. 用户与场景

第一版面向能自己安排三餐的普通成年人：外食和自己做饭都有，愿意花几十秒记一餐。

下面几类人可以打开产品，第一版不把他们当成「按个人目标计算热量缺口」的用户：

- 说出催吐、绝食、只喝茶、暴瘦、不吃饭的人
- 孕妇、备孕、哺乳期，以及未成年人
- 已经勾选或在文字里提到肾病、糖尿病、高血压的人

典型场景：

1. 中午写「一碗牛肉面加个蛋」，或拍一张餐食照片，核对后保存。
2. 晚上打开「今日」，看合计，并看下一餐是哪一道库里的菜。
3. 在「我的」里自己填写每日目标；没确认之前，报告只给合计。

## 3. 功能需求

### 3.1 记录

- 两种入口都要能用：拍照或上传 jpeg / png / webp；或者写一句话，最长 1500 字。
- 照片在浏览器里压缩后再提交。餐食记录不保存照片本身。
- 识别结果是一份待核对的草稿：食物名、分量说法、克数。用户改完再保存。
- 分量可以点「小」「中」「大」，也可以直接改克数。改完后按食物表重算。
- 一餐最多 12 项。餐次为早餐、午餐、晚餐、加餐，可按时间给出默认值。
- 没写字也没选照片时，不提交。
- 未配置模型密钥时，文字按「加、和、逗号」等拆开，再拿食物表做精确匹配。这时只上传照片不会编造食物，提示改为打字。根 README 里「无密钥时照片返回固定的米饭和鸡蛋」与当前代码不一致，以代码和 `tests/nutrition.test.js` 为准。

### 3.2 计算

- 热量和三大营养素只按「每 100 克含量 × 克数 / 100」计算，四舍五入到整数。
- 名字与本地 `foods.csv` 整段相等（含别名）且该行允许计算时，只用本地表。当前仓库 49 条食物，41 条可计算。可计算原料按 USDA FoodData Central 公开领域数据录入并四舍五入，不是《中国食物成分表》。
- 本地不可计算的具体名字：牛肉面、馒头、饺子、小米粥、白粥、面条、挂面、阳春面。配置了薄荷密钥时，按这一次的食物名查询薄荷健康开放平台，再用返回的每 100 克数据在本机乘克数。同名时优先不带品牌前缀的结果，其他放进候选，用户可以改选。
- 「外卖套餐」「套餐」「外卖」太笼统，不查询，请用户拆成具体的菜。
- 没有密钥、没有搜到、超时或接口失败：该项无法估算，不编数字。
- 对上多条本地食物时列为待选择，不自动挑一条来算。
- 食谱不手写热量。20 道菜的营养由原料克数计算。

### 3.3 今日报告

- 只加总当天已经记下的食物。没有记录时说明今天还是空的，不生成报告。
- 展示总热量和蛋白质、脂肪、碳水。无法估算的食物列出名字，不进合计。
- 用户确认过每日目标才对比。没确认时只给合计。
- 建议一两句。句子里的数字必须来自这份合计或已确认的目标；对不上就丢掉这句，页面仍保留合计。
- 有模型密钥时，句子由文本模型写。没有密钥时，由程序按合计和谨慎标记写。

### 3.4 下一餐

- 先由程序从食谱库里选一道，模型只解释为什么是这道。
- 推荐的编号必须在库里。理由若出现其他菜名，或出现对不上的数字，整句丢掉。
- 库里没有合适的，直接说没有，并请用户从现有食谱里另选。
- 不喜欢就换一道。换过的编号不再进入这一次的候选。
- 食谱页可以按全部、清淡、家常、早餐、午餐、晚餐筛选，并打开原料、克数和做法。
- 数据里 20 道仍全部标着 `example=true`，审阅清单在 [家常食谱草稿](14-家常食谱草稿.md)。那份清单写了界面角标是「待审核」。当前「食谱」列表按菜名、约热量、餐次和做法展示，没有根据 `example` 渲染这个角标。

### 3.5 我的与目标

- 每日目标由用户自己填：热量，以及可选的蛋白质、脂肪、碳水。保存前必须勾选「把这些数字当作我的每日目标」。没勾选不能保存。
- 留空的项目不参与对比。热量上限 10000，三大营养素上限 500，只接受非负整数。
- 谨慎情况由用户勾选：孕期或备孕、哺乳、未成年、肾病、糖尿病、高血压、吃饭让我很痛苦或出现催吐与绝食。保存前必须再勾选确认。未确认时，这些勾选不参与报告。
- 文字里出现对应说法时，即使用户没勾选，报告和推荐仍会按谨慎规则处理。
- 清除数据在「我的」里。清除前说明找不回来。清除会去掉这台浏览器上的饮食记录和每日目标。
- 模型提议修改身高、体重、过敏、疾病后再写入的流程，当前代码没有。旧的称呼、目标和饮食偏好表单仍留在代码里，主导航的「我的」不打开它。

### 3.6 邀请码门禁

- 设置了 `INVITE_CODES` 才拦截。本地不设置时，预览可以直接打开。
- 邀请码开启时必须配置 `INVITE_SECRET`。服务签发 cookie，cookie 里没有邀请码原文。
- cookie 名 `zhiyang_invite`，`HttpOnly`、`SameSite=Lax`，大约 90 天。HTTPS 或平台带上 `X-Forwarded-Proto: https` 时带 `Secure`。
- 未解锁时，饮食接口和旧的咨询接口返回「请先填写邀请码」。页面先要求输入邀请码。
- 公网试用入口和可复用邀请码写在 [部署说明](15-公开部署.md) 末尾，也写在 [产品一页纸](产品一页纸.md)。

### 3.7 风险分流

| 情况 | 试用版行为 |
| --- | --- |
| 普通成年人，愿意记录 | 可以记、可以出当天合计、可以从食谱库推荐下一餐 |
| 催吐、绝食、暴瘦、只喝茶、不吃饭，或已确认进食相关痛苦 | 可以留下记录。不按热量缺口鼓励少吃，不夸奖吃得很少 |
| 孕期、备孕、哺乳、未成年 | 可以记录。不套用减重缺口。下一餐按家常搭配，并提示咨询医生或营养专业人员 |
| 糖尿病、高血压 | 可以展示合计。文字说明这不是治疗膳食 |
| 肾病 | 不按蛋白质缺口推荐标了 `kidney_high_protein` 的菜 |
| 呼吸困难、胸痛、呕血、昏迷、自伤等紧急描述 | 只提示立即联系当地急救（中国大陆 120）。不给食谱、不给饮食建议、不留下这一餐草稿 |

关键词分流会漏，也不是医学分诊。紧急判断沿用现有规则：否定、历史或假设句不会被当成当下急救。

## 4. 非功能

### 4.1 本机存储

- 没有产品账号，记录不在服务器上同步。
- 浏览器 IndexedDB，库名 `zhiyang-local-v2`。刷新后饮食记录还在。换浏览器、换设备或清除站点数据后找不到。
- 无法估算的食物不能带热量写入。已匹配的食物必须带有来源、来源说明和版本。

### 4.2 隐私

- 首次打开会说明：照片和文字用来识别这一餐，记录只留在这台设备上，热量是估算，不用于诊断或治疗。
- 有模型密钥时，这一餐的文字或压缩后的照片会发给当前配置的模型服务。服务端不把照片和饮食正文写入日志，也不在服务器上保存它们。
- 需要查询薄荷时，发出的是这一次的食物名。日志记接口、结果和耗时，不记食物名、饮食正文或密钥。
- 薄荷结果有大约 10 分钟的内存缓存，不写入数据库，也不按页把对方食物库拉下来。

### 4.3 性能粗量级

下面是代码里的上限，不是压测成绩。

| 项目 | 代码中的量级 |
| --- | --- |
| 识别请求 | 约 2MB。图片 data URL 超过约 1.8MB 会拒绝 |
| 其他饮食接口 | 约 256KB |
| 旧咨询接口 | 约 48KB |
| 频率 | 同一来源大约 60 秒内超过 40 次，返回「请求较多，请稍后重试」 |
| 模型超时 | 默认 40000 毫秒，可用 `DASHSCOPE_TIMEOUT_MS` 调整 |
| 薄荷超时 | 8 秒。缓存大约 10 分钟，条数上限约 100 |
| 邀请码有效 | cookie 大约 90 天 |

## 5. 明确不做与冻结范围

明确不做：

- 自研专用菜品检测模型
- 让模型编造菜谱、克数或热量
- 图表墙、维生素全表、一周自动配餐、打卡积分、消息推送
- 商城、医生问诊、家庭多成员、舌诊面诊、可穿戴设备、慢病治疗方案
- 账号和云同步。要不要以后做，仍待决定，见 [项目路线图](项目路线图.md)
- 把产品说成医疗器械或精确的营养治疗
- 把《中国食物成分表》整表放进仓库

先冻结，不从仓库删除：体质测评、茶饮、调养专题、养生文章、起居示例、以养生咨询为主的旧对话、十八反和十九畏。这些不是当前主卖点。

当前导航只接受记录、今日、食谱、我的。旧的食养页和调养页函数还在源码里，导航进不去。根 README 写冻结内容收在「我的」的「已冻结的内容」。当前「我的」页面是每日目标、谨慎情况、隐私和清除；样式里有折叠块，页面没有引用。

食谱若写进配伍禁忌原料，推荐前仍会拦住，不作为主流程卖点。

## 6. 验收标准

编号和通过条件沿用产品方案的 B01–B10。下表注明当前试用版做到哪里。本次整理没有打开公网逐条手测；标「待人工核对」的，不能写成已经完成。

| 编号 | 场景 | 通过条件 | 当前试用版 |
| --- | --- | --- | --- |
| B01 | 拍一餐 | 返回菜品和估计分量；热量写「约」；改分量后数字按食物表变化 | 已实现入口、压缩、识图请求，以及「小 / 中 / 大」和改克数后的重算。无模型密钥且只有照片时不编造食物。公网真实照片的识别效果待人工核对 |
| B02 | 「中午一碗牛肉面加个蛋」 | 拆成可核对的食物和分量；对上表的才有热量；对不上的无法估算 | 已实现。自动化覆盖无薄荷密钥：鸡蛋可算，牛肉面无法估算。配置密钥后的线上命中待人工核对 |
| B03 | 看当天报告 | 合计等于当天记录；有目标才对比；建议一两句，且不引入新数字 | 已实现。建议数字对不上会被丢掉 |
| B04 | 要下一餐 | 食谱编号在库中；理由对得上缺口；不出现库外菜名 | 已实现。程序选题，理由不合规则就丢掉。库空时说明不会新编 |
| B05 | 没有记录，或目标没设 | 空状态说清楚；不生成假报告，不把默认目标说成个人处方 | 已实现 |
| B06 | 进食障碍相关说法、孕期、慢病 | 不推极端少吃；不把成人减重目标套到孕妇和未成年人；肾病不按蛋白质缺口推高蛋白 | 已实现程序规则，并有肾病推荐的自动化断言。关键词会漏，不是完整分诊 |
| B07 | 紧急描述 | 只有急救提示，没有食谱和饮食建议 | 已实现。自动化覆盖「我现在呼吸困难」 |
| B08 | 模型要改档案 | 身高、体重、过敏、疾病等写入前有明确确认；用户拒绝则不改 | 用户自己保存目标和谨慎情况前必须勾选，已实现。模型提议修改身高、体重、过敏、疾病的确认队列，当前代码没有，未实现 |
| B09 | 保存、刷新、清除 | 记录在本机还在；清除后找不回，并事先说明 | 程序和 `fake-indexeddb` 测试已覆盖保存、拒绝无法估算食物带热量。真实浏览器手测待人工核对 |
| B10 | 手机和电脑 | 拍照或输入、改分量、看报告、打开推荐食谱，两条路径都能完成 | 待人工核对。页面是同一套，本次没有在手机和电脑上走完 |
