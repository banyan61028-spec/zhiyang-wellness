# 知养：功能测试用例

状态：与当前 `main` 试用版一致。日期：2026-10-07。

表里是可以执行的用例，覆盖主路径和边界。带测试名的条目对应仓库里的 `npm test`。需要打开浏览器或公网的条目，本次文档整理没有逐条手测，执行时把结果记在备注里。

本地预览：`npm ci` 后 `npm test`，再 `npm run dev`，默认 `http://127.0.0.1:8765`。不设置 `INVITE_CODES` 时不要邀请码。公网用例用 [部署说明](15-公开部署.md) 末尾的试用链接和邀请码。

| 编号 | 前置 | 步骤 | 期望 |
| --- | --- | --- | --- |
| TC-01 | 已进入应用。可以不配置模型密钥 | 在「记录」输入「中午一碗牛肉面加个蛋」，提交，核对两项，点「记下来」，打开「今日」 | 拆成牛肉面和鸡蛋。鸡蛋有「约」热量。没有薄荷密钥时牛肉面显示暂时算不出来，不出现编造热量。今日能看到这一餐。对应 B02。自动化：`text stub splits beef noodles and an egg`、`diet API urgent path has no meal, and a normal sentence can be logged` |
| TC-02 | 草稿里有一条已匹配的本地食物，例如米饭 | 点「小」，再点「大」，或把克数改大 | 克数变化，热量按食物表重算，两次数字不同。对应 B01 的改分量。自动化：`portion buttons change grams and the table recalculates` |
| TC-03 | 不配置 `DASHSCOPE_API_KEY` | 只选一张照片，不写文字，提交 | 提示暂时无法识别，请稍后再试或改为打字记录。不出现一份编造的米饭和鸡蛋。自动化：`a photo without a configured model asks the person to type instead of inventing foods` |
| TC-04 | 已配置模型密钥的环境。本次未在公网核对密钥是否开启 | 拍或上传一张真实餐食照片，提交 | 返回若干食物和估计分量，热量写「约」。识别错了可以改食物或克数后再算。公网真实照片效果待人工核对。对应 B01 |
| TC-05 | 当天没有任何饮食记录 | 打开「今日」 | 说明今天还没记，没有合计，没有一份编出来的报告。对应 B05。自动化：空 `meals` 时 `mode` 为 `empty` |
| TC-06 | 当天至少有一条可计算记录。还没在「我的」确认目标 | 打开「今日」 | 有合计。说明还没确认每日目标，不把空白目标说成已经对比过。对应 B03、B05 |
| TC-07 | 打开「我的」的每日目标 | 不勾选确认就点保存；再填一个热量，勾选「把这些数字当作我的每日目标」后保存，回到「今日」 | 未勾选时提示先勾选确认，不保存。确认后今日出现与所填热量的差距。留空的蛋白质不参与对比。对应 B03、B08 的用户确认部分 |
| TC-08 | 当天有记录，食谱数据能打开 | 在「今日」看下一餐，打开这道菜，再点「换一道」 | 菜名来自食谱库，能看到原料、克数和做法。换一道后编号与刚才不同（库里还有其他菜时）。没有合适的会说明不会新编一道。对应 B04。自动化：`advice keeps only numbers from the calculation and recommendation stays inside the library` |
| TC-09 | 已进入应用 | 输入「外卖套餐」或「外卖」并提交 | 提示说法笼统，请写成具体的菜。没有热量，也不会去查薄荷。自动化：`non-calculable dishes are looked up live, and vague names are not sent` |
| TC-10 | 不设置 `BOOHEE_API_KEY` | 分别记录「馒头」「饺子」「小米粥」「白粥」「面条」 | 每一项都无法估算，不出现热量。这些名字在本地表里标为不可计算。自动化：`chinese porridge and noodle names are not filled from a different USDA food`、`missing key ... stay unestimated` |
| TC-11 | 测试里用模拟的薄荷响应。公网是否配置了真实密钥，待人工核对 | 在配置了密钥的自动化里识别「中午一碗牛肉面」；另测空结果和 HTTP 失败 | 有结果时来源为薄荷健康，热量由返回的每 100 克数据乘克数。空结果或失败时保持无法估算。品牌菜可作为候选，不压过同名的非品牌结果。自动化：`tests/boohee.test.js` |
| TC-12 | 已进入应用 | 在记录框输入「我现在呼吸困难」并提交；再到「今日」若正文里带有同类紧急描述 | 只出现急救提示，正文要求联系当地急救（中国大陆 120）。没有食物草稿、食谱和饮食建议。对应 B07。自动化：`diet API urgent path` 与 `urgent cases return help only` |
| TC-13 | 当天有可计算记录 | 在「我的」勾选肾病，勾选确认后保存。或在记录原文里写「肾病」 | 推荐菜的 `avoid` 不含 `kidney_high_protein`。不按蛋白质缺口推高蛋白菜。对应 B06。自动化：肾病推荐断言 |
| TC-14 | 无模型密钥，便于核对固定句子。有密钥时句子由模型写，仍须通过数字检查 | 记录原文包含「绝食」，或勾选并确认「吃饭让我很痛苦，或出现催吐、绝食」，再看今日建议 | 不按热量缺口鼓励少吃。无密钥时程序句说明记录已经留下，并提示寻求专业帮助。对应 B06 |
| TC-15 | 已保存至少一餐，并确认过一个目标 | 刷新页面。再到「我的」打开清除，先看说明，确认清除，再刷新 | 刷新后记录还在。清除前说明找不回来。确认后饮食记录和每日目标都没有了。对应 B09。存储自动化使用 `fake-indexeddb`，真实浏览器待人工核对 |
| TC-16 | 公网试用链接。另备一个未设置 `INVITE_CODES` 的本地预览 | 公网先输入错误码，再输入 `zhiyang-try-a`（`zhiyang-try-b`、`zhiyang-try-c` 同样可复用）。本地直接打开 | 错误码不能进入。正确码进入后可以记录。本地不设置邀请码时不拦截。cookie 大约 90 天，里面没有邀请码原文。自动化：`tests/invite.test.js`（用的是测试码，不是这三枚公网码） |
| TC-17 | 仓库根目录，依赖已安装 | 运行 `npm test` | 进程退出码为 0。覆盖热量公式、导入校验、匹配失败不产生数字、本地不可计算再问薄荷、笼统外卖不查，以及分流、邀请码和本机存储 |
| TC-18 | 一台手机和一台电脑，都能打开同一试用地址 | 两边各自完成：输入或拍照、改分量、看今日、打开推荐食谱 | 四步都能做完。手机用页面上的文件选择拍照。本次整理未执行，对应 B10，结果待人工核对 |

建议数字被丢掉、推荐理由写了别的菜名就被丢掉，已经包含在 TC-08 指向的那条自动化里：句子出现允许列表之外的数字，或提到另一道菜名时，`kept` 为 false。
